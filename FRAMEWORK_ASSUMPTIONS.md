# Framework Assumptions & Design Contracts

This file documents the assumptions the framework currently meets and is expected to meet.
It is a living document — updated across sessions.

---

## 1. Architecture & Environment

- **Runtime**: .NET 8, NUnit 4, RestSharp, Autofac DI, FluentAssertions, Allure, Bogus
- **Services**: AuthService (5300), ProductService (5100), OrderService (5200), ImportService (5400)
- **Infrastructure**: SQL Server (EF Core `EnsureCreated`) + Redis (distributed cache)
- **Assumption**: Services MUST be running before tests execute. The framework does not start services on its own.
- **Configuration**: `appsettings.test.json` + Consul KV (Consul optional — falls back to JSON)

---

## 2. Test Data Isolation

- **Each test creates its own data** — no shared fixtures between tests
- **No cleanup after test** — the database is not reset; tests must be deterministic without assuming a clean state
- **Data generated by Bogus** — random, realistic, unique (e.g. `faker.Internet.Email()` minimises collisions)

## 3. Cross-Service Dependencies

### Current state — handled by Step classes

| Scenario | Pattern |
|---|---|
| OrderService requires an existing `productId` | `OrderServiceSteps.CreateOrderWithProductAsync()` — internally calls `ProductServiceSteps.CreateProductAsync()` before creating the order |
| ImportService may require existing products/orders | TBD — no implementation yet |

### Test generator assumption

When a swagger endpoint has a `requestBody` field that looks like a foreign key (e.g. `productId`, `orderId`, `userId`):
1. The generator recognises the `*Id` pattern in the request body schema
2. Generates code that first creates the resource via the appropriate Step (e.g. `_productSteps.CreateProductAsync()`)
3. Uses the returned ID as the input parameter

### Foreign key → Step class mapping (convention)

| Field in body | Step class | Method |
|---|---|---|
| `productId` | `ProductServiceSteps` | `CreateProductAsync()` |
| `orderId` | `OrderServiceSteps` | `CreateOrderWithProductAsync()` |
| `userId` | `AuthServiceSteps` | `RegisterUserAsync()` |

- **Assumption**: The `{resource}Id` naming convention is sufficient to detect dependencies
- **Limitation**: If the field does not match the convention (e.g. `referenceNumber`), the generator emits `// TODO: provide valid {field} value` in a comment

### Predefined (seed) data

- **Current state**: No seed data — everything is created dynamically per test
- **TODO**: Consider a `test-seeds.json` file for data that must exist before tests run (e.g. a fixed product with ID=1 for integration tests that cannot create resources)
- **TODO**: Add a `GlobalSetup` step that verifies prerequisites (services are alive, seed data exists)

## 4. Authorization & Tokens

- **JWT** required for most endpoints (declared via `security` in swagger)
- **`TokenProvider`**: global token set once in `GlobalSetup` (admin user)
- **`TestTokenContext`** (`AsyncLocal`): per-test token — overrides the global token
- **`TokenScope`**: synchronous disposable; MUST be called in the test method context (not inside an async helper)
- **`UserScope`**: registers a new user and sets their token as active
- **Generator assumption**: If an endpoint has `security` in swagger → test generates `UserScope` setup; otherwise → no token setup

## 5. Test Generation from OpenAPI

### Current state — `--mode tests` (scaffold)

- Generates stubs with `Assert.Inconclusive` for every documented response code
- Includes AAA comments with arrange/assert hints
- Output to `artifacts/generated-tests/` — NOT compiled as part of the test project
- Executed via `generate-tests.bat`

### Goal — `--mode impl` (implementation)

The generator should produce fully compilable, runnable tests. Rules:

#### Per response code:

| Code | Arrange strategy | Assert strategy |
|---|---|---|
| 200/201 | Create valid data via Step; if GET/PUT/DELETE requires an ID — POST first | `ShouldHaveStatusCode` + `ShouldHaveData()` + field assertions from response schema |
| 400 | Send body with missing `required` fields or invalid values | `ShouldHaveStatusCode(BadRequest)` |
| 401 | Call endpoint without a token (empty `TokenScope`) | `ShouldHaveStatusCode(Unauthorized)` |
| 403 | Call endpoint with a `User`-role token on an admin-only endpoint | `ShouldHaveStatusCode(Forbidden)` |
| 404 | Use `int.MaxValue` as the ID | `ShouldHaveStatusCode(NotFound)` |
| 409 | Create a resource, then attempt to create it again with the same unique data | `ShouldHaveStatusCode(Conflict)` |

#### Foreign key detection in body:

```
requestBody.schema.properties → look for fields ending in "Id"
→ check mapping (Section 3)
→ if known: generate `await _productSteps.CreateProductAsync()` before the test body
→ if unknown: generate comment `// TODO: provide valid {fieldName}`
```

#### Response field assertions:

```
responses.200.content.schema.properties → for each top-level field
→ generate `data.{PropertyName}.Should().NotBeNull()` or `.Be(expected.{PropertyName})`
→ for fields present in the request body: compare against the Arrange value
```

## 6. Naming Conventions

- **Step classes**: `{Service}ServiceSteps` — one class per service
- **Step methods**: `{Verb}{Resource}Async` e.g. `CreateProductAsync`, `GetOrderAsync`
- **Data generators**: `{Service}DataGenerator.Generate{Resource}Request()`
- **Test names**: `{Method}_{Resource}_{Scenario}_Returns{StatusCode}`
- **Generated files**: `{Service}GeneratedTests.g.cs` — `.g.cs` suffix marks a generated file

---

## 7. Reporting

- **Allure**: Every Step annotated with `[AllureStep]`
- **Serilog**: Every HTTP request logged by `ApiClient`
- **NUnit categories**: `[Category("GET")]`, `[Category("Success")]`, `[Category("Security")]` etc.

## 8. CI/CD

- **Jenkins**: multibranch pipeline `api-tests-framework-multibranch`
- **Requirement**: Jenkins build must pass before a PR is merged
- **Docker Compose**: services started by Jenkins in containers during the build
- **Assumption**: `develop` is the base branch for PRs; `main` = production
