✅ Czyste 4-warstwowe rozdzielenie odpowiedzialności
ZALETA

Framework stosuje klasyczny wzorzec warstwowy: Clients (DTOs/kontrakty), Core (infrastruktura HTTP, DI, asercje), Steps (biznesowe kroki testów), Tests (scenariusze). Każda warstwa ma jedno zadanie. Warstwy zależą tylko od niższych — nie ma odwróconych zależności.

✅ Allure + FluentAssertions + Bogus — dobry dobór bibliotek
ZALETA

Allure.NUnit zapewnia bogate raporty ze zrzutami request/response. FluentAssertions daje czytelne asercje. Bogus generuje realistyczne dane testowe bez powtórzeń. Autofac jako DI jest przesadą dla projektu tej wielkości, ale nie jest błędem.

✅ RequestBuilder — elegancki fluent API
ZALETA

Płynny budowniczy z metodami WithMethod(), WithPath(), WithPathSegment(), WithBody() itd. jest czytelny i rozszerzalny. RequestFactory jako skróty do typowych wywołań to dobra obserwacja DRY.

⚠️ OpenApi projekt — infrastruktura bez integracji
DROBNA

ApiTestFramework.OpenApi zawiera OpenApiSpecLoader i TestCaseScaffolder, ale nigdzie nie są one wywoływane — ani z Jenkinsa, ani z samego pipeline'u testowego. Projekt nie jest częścią ApiTestFramework.sln (brak w pliku .sln). Obecność "martwego" projektu może mylić nowych deweloperów.

PROBLEM

🔍Jakość kodu — szczegółowe ustalenia
🔴 GlobalSetup używa hardkodowanej nazwy użytkownika — kruchy design
KRYTYCZNY

W GlobalSetup.cs rejestrowany jest stały użytkownik "test_user_global". Jeśli baza danych nie zostanie wyczyszczona (np. podczas debugowania lokalnego bez docker compose down -v), drugi run zwróci 409 Conflict i cały suite padnie przed uruchomieniem jakiegokolwiek testu.

Poprawka: zamiast rejestracji użyć logowania jeśli rejestracja zwróci 409, albo generować losową nazwę użytkownika (AuthDataGenerator.GenerateRegisterRequest() już to robi).

// PROBLEM:
var registerRequest = new RegisterRequest {
    Username = "test_user_global",   // ← hardkodowane!
    Email    = "test_global@test.com",
    ...
};
// POPRAWKA:
var registerRequest = AuthDataGenerator.GenerateRegisterRequest();
tests/ApiTestFramework.Tests/GlobalSetup.cs : linia ~35
🔴 ConfigurationProvider — potencjalny race condition przy inicjalizacji
KRYTYCZNY

Właściwość Configuration sprawdza _configuration == null bez blokady (lock). W środowisku równoległym (a NUnit 4 domyślnie może uruchamiać fixtures równolegle) dwa wątki mogą jednocześnie wejść do bloku inicjalizacji i zbudować dwa oddzielne obiekty konfiguracji.

// PROBLEM:
if (_configuration == null) {    // ← brak lock!
    _configuration = new ConfigurationBuilder()...Build();
}

// POPRAWKA — Lazy<T>:
private static readonly Lazy<IConfiguration> _lazyConfig = new(() =>
    new ConfigurationBuilder()...Build());
public static IConfiguration Configuration => _lazyConfig.Value;
tests/ApiTestFramework.Core/Configuration/ConfigurationProvider.cs
🟠 CreateOrder_WithInvalidProduct_ReturnsBadRequest — zepsuty test
POWAŻNY

Ten test jest wadliwy pod kilkoma względami:

1. Pierwsze wywołanie _orderSteps.GetOrderAsync(0) jest całkowicie nieużywane — to martwy kod.

2. Test ręcznie rozwiązuje ApiClient z kontenera zamiast używać abstrakcji StepClass, co przełamuje warstwy architektoniczne.

3. Klasa OrderServiceSteps nie ma metody TryCreateOrderAsync() dla scenariuszy negatywnych, co zmusiło autora do obejścia przez bezpośredni dostęp do kontenera.

// PROBLEM:
var response = await _orderSteps.GetOrderAsync(0); // ← nieużywane!
var apiClient = ContainerProvider.ResolveNamed<ApiClient>("OrderService");
var rawResponse = await apiClient.SendAsync(...);   // ← przełamuje abstrakcję

// POPRAWKA — dodaj do OrderServiceSteps:
public async Task<RestResponse<Order>> TryCreateOrderAsync(CreateOrderRequest req)
    => await _client.SendAsync<Order>(RequestFactory.Post(OrderServiceRoutes.Base, req));

💡Analiza zasady KISS (Keep It Simple, Stupid)

✅ Gdzie KISS jest zachowany

  • RequestFactory — jednoliniowe skróty bez magii
  • BaseTest — prosty cykl życia, bez nadmiernej abstrakcji
  • DataGenerators — statyczne klasy, zero konfiguracji
  • Routes.cs — proste stałe string, nic więcej
  • Wzorzec Tests → Steps → ApiClient jest liniowy i przewidywalny
  • Testy mają Arrange/Act/Assert wyraźnie rozdzielone

❌ Gdzie KISS jest naruszony

  • Autofac DI dla 3 obiektów tej samej klasy — przesada
  • Dwa globalne singletony (TokenProvider + ContainerProvider) obok Autofac
  • RequestBuilder._contentType — martwa gałąź komplikuje logikę
  • TestConfiguration + ApiClientModule — dwa miejsca do aktualizacji per nowy serwis
  • OpenApi projekt — martwy kod w rozwiązaniu
  • Podwójne logowanie (w ApiClient i w każdej klasie Steps)
🟠 Autofac jest przesadą dla trzech instancji ApiClient
KISS naruszony

Framework używa pełnego kontenera IoC Autofac wyłącznie po to, żeby zarejestrować 3 named instancje ApiClient. Dodatkowo ContainerProvider jest statycznym singletonen — więc de facto Autofac jest wrapperem na słownik. Prosta alternatywa:

// Prosta klasa "serwisów" zastępująca Autofac + ContainerProvider:
public static class ApiClients
{
    public static ApiClient Auth    { get; private set; } = null!;
    public static ApiClient Product { get; private set; } = null!;
    public static ApiClient Order   { get; private set; } = null!;
    
    public static void Initialize(TestConfiguration config) {
        Auth    = new ApiClient(config.AuthService.BaseUrl, "AuthService");
        Product = new ApiClient(config.ProductService.BaseUrl, "ProductService");
        Order   = new ApiClient(config.OrderService.BaseUrl, "OrderService");
    }
}

Zaletą obecnego rozwiązania jest jednak to, że łatwo można w przyszłości dodać bardziej złożony DI (mock serwisy, dekoratory). Jeśli framework ma rosnąć, Autofac ma sens. Przy obecnej skali — nie.

🟡 TokenProvider + Autofac — dwa różne mechanizmy do tego samego
KISS

Framework ma dwa niezależne mechanizmy do przechowywania globalnego stanu: ContainerProvider (Autofac) do klientów API, i TokenProvider (własny statyczny singleton) do tokenu JWT. Logika auto-inject tokenu w RequestBuilder.Build() to ukryty efekt uboczny — budowanie requestu nie powinno mieć dostępu do globalnego stanu autoryzacji. Token powinien być dodawany w ApiClient.ExecuteAsync() lub przekazywany explicite.

🟠 Auto-inject tokenu w RequestBuilder.Build() narusza SRP
POWAŻNY

Metoda Build() ma ukryty efekt uboczny — odczytuje globalny stan z TokenProvider. Budowniczy requestu nie powinien wiedzieć o tokenach autoryzacji. To zadanie ApiClient.ExecuteAsync():

// PROBLEM — w RequestBuilder.Build():
if (!_headers.ContainsKey("Authorization") && TokenProvider.HasToken)
    _headers["Authorization"] = $"Bearer {TokenProvider.Token}";

// POPRAWKA — przenieś do ApiClient.ExecuteAsync():
public async Task<RestResponse> ExecuteAsync(RestRequest request) {
    if (!request.Parameters.Any(p => p.Name == "Authorization")
        && TokenProvider.HasToken)
        request.AddHeader("Authorization", $"Bearer {TokenProvider.Token}");
    // ...
}
🟡 Podwójne logowanie: Steps + ApiClient
DROBNA

Każda klasa Steps loguje "Creating product: {Name}" itp., a ApiClient.ExecuteAsync() loguje "[ProductService] POST /api/products". W konsoli Jenkins widoczne są dwa logi na każde wywołanie. Steps powinny albo nie logować (bo ApiClient to robi), albo logować tylko informacje biznesowe nieobjęte przez ApiClient.

🟡 CreateProductAndReturnIdAsync() — zbędny wrapper
DROBNA

Metoda CreateProductAndReturnIdAsync() jest jednolinijkowym wrapperem na CreateProductAsync(). Taki wrapper nie jest wart tworzenia osobnej metody z atrybutem [AllureStep]. Wystarczy: (await _productSteps.CreateProductAsync()).Id w miejscu użycia.

✅ OrderServiceSteps.CreateOrderWithProductAsync() — dobra enkapsulacja zależności
ZALETA

Metoda enkapsuluje zależność Order→Product: tworzy produkt, potem zamówienie. Testy nie muszą wiedzieć o cross-service dependency — dostają gotowy stan. To właściwy poziom abstrakcji dla klasy Steps.

✅ Wzorzec "Try*" w AuthServiceSteps — dobra konwencja dla testów negatywnych
ZALETA

Konwencja "szczęśliwa ścieżka zwraca DTO, Try-wariant zwraca raw RestResponse" jest elegancka. Testy asertują status kod bezpośrednio bez try/catch. Należy rozszerzyć ten wzorzec na Product i Order steps.

🎯Rekomendacje priorytetowe
P1 — Krytyczny

Napraw hardkodowaną nazwę użytkownika w GlobalSetup

Zastąp statyczną nazwę "test_user_global" wywołaniem AuthDataGenerator.GenerateRegisterRequest(). Zapobiegnie to błędom przy lokalnych uruchomieniach z persystentną bazą danych.

P1 — Krytyczny

Napraw thread safety w ConfigurationProvider

Użyj Lazy<IConfiguration> lub dodaj lock(_lockObj) wokół inicjalizacji _configuration. Bez tego jest potencjalny race condition w równoległym środowisku.

P2 — Poważny

Dodaj metody Try* do ProductServiceSteps i OrderServiceSteps

Wzoruj się na AuthServiceSteps.TryRegisterUserAsync(). Dodaj TryCreateProductAsync(), TryUpdateProductAsync(), TryCreateOrderAsync() itd. Umożliwi to poprawne testy negatywne bez omijania warstwy Steps.

P2 — Poważny

Napraw test CreateOrder_WithInvalidProduct_ReturnsBadRequest

Usuń martwe wywołanie GetOrderAsync(0). Po dodaniu TryCreateOrderAsync() użyj tej metody zamiast bezpośredniego dostępu do kontenera Autofac.

P2 — Poważny

Przenieś auto-inject tokenu z RequestBuilder do ApiClient

Budowniczy nie powinien mieć dostępu do globalnego stanu. Przenieś logikę TokenProvider.HasToken do ApiClient.ExecuteAsync(). Uprości to RequestBuilder i naprawi test ProductService_WithoutToken.

P2 — Poważny

Usuń duplikat AuditInfo — wspólny namespace Clients.Common

Przenieś AuditInfo do nowego pliku Dtos/CommonDtos.cs w namespace ApiTestFramework.Clients.Common. Usuń kopie z ProductDtos.cs i OrderDtos.cs.

P3 — Ważny

Zmień TestConfiguration na Dictionary dla serwisów

Zmień trzy osobne właściwości ServiceConfig na Dictionary<string, ServiceConfig> Services. ApiClientModule będzie mógł iterować i rejestrować klientów automatycznie — dodanie nowego serwisu nie wymaga zmiany kodu C#.

P3 — Ważny

Usuń lub zintegruj projekt ApiTestFramework.OpenApi

Albo dodaj projekt do sln i zintegruj scaffolding w procesie CI, albo usuń go. Martwy projekt w rozwiązaniu wprowadza zamieszanie. Jeśli zostaje, dodaj README z instrukcją użycia.

P3 — Ważny

Usuń komentarze "PLACEHOLDER" z DTOs

DTOs są produkcyjne i używane w 22 testach. Komentarze "will be replaced by NSwag" są mylące. Zaktualizuj je lub usuń. Jeśli NSwag ma być używany, zrób to — jeśli nie, usuń NSwag z zależności.

P4 — Ulepszenie

Usuń martwy kod: RequestBuilder._contentType

Usuń pole _contentType, metodę WithContentType() i gałąź w Build(). Upraszcza kod i eliminuje niepotrzebną złożoność.

P4 — Ulepszenie

Usuń CreateProductAndReturnIdAsync()

Jednoliniowy wrapper nie zasługuje na osobną metodę z [AllureStep]. Użyj (await CreateProductAsync()).Id bezpośrednio w miejscu użycia.

P4 — Ulepszenie

Stałe dla "nieistniejących ID" w testach

Zastąp magiczną liczbę 99999 nazwaną stałą np. private const int NonExistentId = 99999; w klasie BaseTest lub osobnym pliku stałych testowych.
